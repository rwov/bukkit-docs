# Worlds and locations

A `World` is live server state. A `Location` combines a world reference, coordinates, yaw, and pitch; persistent storage should usually keep the world UUID or name plus numeric fields.

## Resolve worlds

- Use `Bukkit.getWorld(UUID)` when a durable world identity is available.
- A stored world may be missing, renamed, or not loaded.
- Create/load worlds with `WorldCreator` during controlled lifecycle work.
- Do not assume the first world or a hard-coded name is always correct.

## Locations and teleports

- Clone mutable `Location` objects before changing them.
- Validate finite coordinates and an allowed world.
- Load or generate the destination chunk intentionally, then find a safe floor and headroom.
- Re-check that the player is online and the destination world remains loaded before delayed teleport.

## Unload

- Move or reject players before unloading.
- Flush plugin-owned world data and release chunk tickets.
- Call unload with a deliberate save choice.
- Drop cached world references after success.

## Example

```java
World world = Bukkit.getWorld(savedWorldId);
if (world == null) throw new IllegalStateException("Destination world is unavailable");
Location destination = new Location(world, x, y, z, yaw, pitch);
if (!world.getWorldBorder().isInside(destination)) return;
player.teleport(destination);
```

## Production checklist

- Validate identity, world, and feature ownership at the point of mutation.
- Keep main-thread work bounded; move only isolated data work off-thread.
- Handle disconnect, unload, reload, and disable explicitly.
- Read the exact API contract for the server version you target.
