# Loot tables

Vanilla loot tables are keyed data-driven reward definitions. Bukkit can resolve a registered table and populate/generate loot using a `LootContext`; custom reward systems should preserve the same explicit context and idempotency.

## Vanilla tables

- Resolve a table from a `NamespacedKey` and handle it being absent.
- Build context from the relevant location and optional looted entity, killer, luck, or other supported values.
- Use the provided random source or a documented deterministic source for tests.
- Do not mutate a shared table definition.

## Custom rewards

- Separate eligibility, roll, and delivery.
- Record a claim or transaction identifier before delivering valuable rewards.
- Log enough context to audit rare or economic drops without exposing sensitive data.
- Handle full inventories and disconnected players deliberately.

## Events and ownership

- Use loot-generation events when modifying vanilla output.
- Respect cancellation and modifications from other plugins.
- Tag custom items with PDC.
- Avoid expensive database or HTTP calls inside a loot event; preload or defer a bounded transaction.

## Example

```java
LootTable table = Bukkit.getLootTable(new NamespacedKey("minecraft", "chests/simple_dungeon"));
if (table != null) {
    LootContext context = new LootContext.Builder(location).luck(player.getLuck()).build();
    Collection<ItemStack> loot = table.populateLoot(ThreadLocalRandom.current(), context);
}
```

## Production checklist

- Validate the current object type, ownership, and lifecycle before mutation.
- Bound hot-path loops and spatial work.
- Respect cancellation and changes made by other plugins.
- Remove plugin-owned runtime state during feature shutdown.
