Bukkit gives you a straightforward pipeline for adding custom `/` commands to your plugin: declare the command's metadata in `plugin.yml`, implement `CommandExecutor` to handle executions, and optionally implement `TabCompleter` to drive the suggestion list players see when they press Tab. Every piece is wired together in your plugin's `onEnable()` method, and the full `CommandSender` hierarchy lets you handle both players and console uniformly.

## Declaring a Command in plugin.yml

Every command your plugin handles must be declared under the `commands:` key in `plugin.yml` before it can be registered at runtime. Bukkit reads this file when it loads your plugin and reserves the command name.

```yaml plugin.yml
name: MyPlugin
version: 1.0.0
main: com.example.myplugin.MyPlugin
api-version: 1.20

commands:
  greet:
    description: Greet an online player.
    usage: /greet <player>
    aliases:
      - hello
      - hi
    permission: myplugin.greet
    permission-message: §cYou don't have permission to use this command.
```

| Field | Required | Purpose |
|---|---|---|
| `description` | Recommended | Human-readable description shown in `/help` |
| `usage` | Recommended | Sent to the sender when `onCommand` returns `false` |
| `aliases` | Optional | Additional names that trigger the same executor |
| `permission` | Optional | Bukkit hides the command from players who lack this node |
| `permission-message` | Optional | Message shown when the sender lacks `permission` |

## Implementing CommandExecutor

Create a class that implements `org.bukkit.command.CommandExecutor` and override `onCommand`. The method receives four arguments:

| Parameter | Type | Description |
|---|---|---|
| `sender` | `CommandSender` | Who ran the command (player, console, command block, …) |
| `command` | `Command` | The `Command` object with metadata from `plugin.yml` |
| `label` | `String` | The alias the sender actually typed |
| `args` | `String[]` | Whitespace-split arguments after the command name |

Return `true` when your executor handled the command (even if the usage was wrong). Return `false` to tell Bukkit to print the `usage:` string from `plugin.yml` automatically.

```java GreetCommand.java
package com.example.myplugin;

import org.bukkit.Bukkit;
import org.bukkit.command.Command;
import org.bukkit.command.CommandExecutor;
import org.bukkit.command.CommandSender;
import org.bukkit.entity.Player;

public class GreetCommand implements CommandExecutor {

    @Override
    public boolean onCommand(CommandSender sender, Command command, String label, String[] args) {
        if (args.length != 1) {
            // Return false to trigger the usage message from plugin.yml
            return false;
        }

        String targetName = args[0];
        Player target = Bukkit.getPlayerExact(targetName);

        if (target == null) {
            sender.sendMessage("§cPlayer '" + targetName + "' is not online.");
            return true; // Handled — don't show the usage string
        }

        target.sendMessage("§e" + sender.getName() + " says hello!");
        sender.sendMessage("§aYou greeted " + target.getName() + ".");
        return true;
    }
}
```

<Note>
  Returning `false` does **not** indicate an error — it is simply the signal for Bukkit to display the `usage:` message. Return `true` whenever you have already communicated what went wrong to the sender yourself.
</Note>

## Checking Sender Type

`CommandSender` is the supertype for every source that can run a command. You often need to narrow the type before using player-specific methods:

<Tabs>
  <Tab title="Require a Player">
    ```java SenderTypeCheck.java

    public boolean onCommand(CommandSender sender, Command command, String label, String[] args) {
        if (!(sender instanceof Player)) {
            sender.sendMessage("§cThis command can only be run by a player.");
            return true;
        }

        Player player = (Player) sender;
        player.sendMessage("§aYour location: " + player.getLocation());
        return true;
    }
    ```

    @Override
    public boolean onCommand(CommandSender sender, Command command, String label, String[] args) {
        String displayName;

        if (sender instanceof Player) {
            displayName = ((Player) sender).getDisplayName();
        } else {
            // ConsoleCommandSender or other non-player source
            displayName = "Console";
        }

        Bukkit.broadcastMessage("§6" + displayName + " triggered a global event!");
        return true;
    }

## Tab Completion

Implement `org.bukkit.command.TabCompleter` to control the suggestion list shown when a player presses Tab. The `onTabComplete` method receives the same `sender`, `command`, `label`, and `args` parameters as `onCommand`. Return a `List<String>` of possible completions for the last (partial) argument, or `null` to fall back to the command executor's default tab completion.

Use `StringUtil.copyPartialMatches` from `org.bukkit.util.StringUtil` to filter a list of candidates down to those that start with what the player has already typed:

```java GreetTabCompleter.java
package com.example.myplugin;

import java.util.ArrayList;
import java.util.List;
import org.bukkit.Bukkit;
import org.bukkit.command.Command;
import org.bukkit.command.CommandSender;
import org.bukkit.command.TabCompleter;
import org.bukkit.entity.Player;
import org.bukkit.util.StringUtil;

public class GreetTabCompleter implements TabCompleter {

    @Override
    public List<String> onTabComplete(CommandSender sender, Command command,
                                      String label, String[] args) {
        if (args.length == 1) {
            // Collect all online player names
            List<String> onlineNames = new ArrayList<>();
            for (Player player : Bukkit.getOnlinePlayers()) {
                onlineNames.add(player.getName());
            }

            // Filter to names that start with what the sender has typed so far
            List<String> completions = new ArrayList<>();
            StringUtil.copyPartialMatches(args[0], onlineNames, completions);
            return completions;
        }

        return new ArrayList<>(); // No suggestions for further arguments
    }
}
```

## Registering the Executor

Wire your executor and tab completer to the command name in `onEnable()`. Use `getCommand("name")` — which returns the `PluginCommand` for a name declared in `plugin.yml` — then call `setExecutor` and `setTabCompleter`:

```java MyPlugin.java
package com.example.myplugin;

import org.bukkit.plugin.java.JavaPlugin;

public final class MyPlugin extends JavaPlugin {

    @Override
    public void onEnable() {
        GreetCommand greetCommand = new GreetCommand();
        GreetTabCompleter greetCompleter = new GreetTabCompleter();

        getCommand("greet").setExecutor(greetCommand);
        getCommand("greet").setTabCompleter(greetCompleter);
    }
}
```

If your executor class also implements `TabCompleter`, you can pass the same instance to both methods:

```java MyPlugin.java (single class)
@Override
public void onEnable() {
    GreetHandler handler = new GreetHandler(); // implements both interfaces
    getCommand("greet").setExecutor(handler);
    getCommand("greet").setTabCompleter(handler);
}
```

## Full Example: `/greet <player>`

Below is the complete, self-contained implementation of a `/greet` command with tab completion for online player names:

```java GreetHandler.java
package com.example.myplugin;

import java.util.ArrayList;
import java.util.List;
import org.bukkit.Bukkit;
import org.bukkit.command.Command;
import org.bukkit.command.CommandExecutor;
import org.bukkit.command.CommandSender;
import org.bukkit.command.TabCompleter;
import org.bukkit.entity.Player;
import org.bukkit.util.StringUtil;

public class GreetHandler implements CommandExecutor, TabCompleter {

    // ---------------------------------------------------------------
    // Execution
    // ---------------------------------------------------------------
    @Override
    public boolean onCommand(CommandSender sender, Command command, String label, String[] args) {
        if (!sender.hasPermission("myplugin.greet")) {
            sender.sendMessage("§cYou don't have permission to use this command.");
            return true;
        }

        if (args.length != 1) {
            return false; // Triggers the usage: string from plugin.yml
        }

        Player target = Bukkit.getPlayerExact(args[0]);
        if (target == null) {
            sender.sendMessage("§cPlayer '" + args[0] + "' is not online.");
            return true;
        }

        target.sendMessage("§e" + sender.getName() + " waves hello at you!");
        sender.sendMessage("§aYou greeted §f" + target.getName() + "§a.");
        return true;
    }

    // ---------------------------------------------------------------
    // Tab completion
    // ---------------------------------------------------------------
    @Override
    public List<String> onTabComplete(CommandSender sender, Command command,
                                      String label, String[] args) {
        if (args.length == 1) {
            List<String> names = new ArrayList<>();
            for (Player p : Bukkit.getOnlinePlayers()) {
                names.add(p.getName());
            }
            List<String> completions = new ArrayList<>();
            StringUtil.copyPartialMatches(args[0], names, completions);
            return completions;
        }
        return new ArrayList<>();
    }
}
```

```yaml plugin.yml
commands:
  greet:
    description: Greet an online player.
    usage: /greet <player>
    aliases: [hello, hi]
    permission: myplugin.greet
```

```java MyPlugin.java (registration)
@Override
public void onEnable() {
    GreetHandler handler = new GreetHandler();
    getCommand("greet").setExecutor(handler);
    getCommand("greet").setTabCompleter(handler);
}
```

<Tip>
  You can make your main plugin class implement both `CommandExecutor` and `TabCompleter` and pass `this` to `setExecutor` and `setTabCompleter`. This works well for tiny plugins but becomes hard to maintain as the number of commands grows — prefer separate handler classes instead.
</Tip>
