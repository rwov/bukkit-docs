# Persistent data containers

`PersistentDataContainer` stores plugin-owned primitive data on supported Bukkit holders. Keys are namespaced, values use an explicit `PersistentDataType`, and the data follows the holder's normal persistence lifecycle.

## Keys and types

- Create keys with `new NamespacedKey(plugin, "name")`.
- Read with the same key and data type used to write.
- Use `has`, `get`, and `getOrDefault` without confusing a missing key with a zero/empty value.
- Prefer compact primitives, strings, byte arrays, or nested containers supported by the target API.

## Schema design

- Store a schema version beside nontrivial payloads.
- Use one key per independently evolving field or a well-defined encoded value.
- Validate lengths, ranges, enum names, UUIDs, and references after reading.
- Migrate old versions on a controlled path and keep migration idempotent.

## Holder behavior

- For `ItemMeta`, write the changed meta back to the stack.
- Entity, chunk, world, and tile-state persistence follows their save/update lifecycle.
- PDC is not a database query layer and is poor for global cross-object indexes.
- Remove obsolete keys when ownership ends or migration completes.

## Example

```java
NamespacedKey typeKey = new NamespacedKey(plugin, "item_type");
ItemMeta meta = item.getItemMeta();
meta.getPersistentDataContainer().set(typeKey, PersistentDataType.STRING, "recall_crystal");
item.setItemMeta(meta);

String type = item.getItemMeta().getPersistentDataContainer()
    .get(typeKey, PersistentDataType.STRING);
```

## Failure checklist

- Define timeouts, limits, and ownership at the boundary.
- Validate decoded values before they reach gameplay logic.
- Make retries and duplicate delivery idempotent where necessary.
- Close clients, pools, executors, and registrations during disable.
