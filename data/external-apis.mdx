# HTTP and external APIs

HTTP is a slow and failure-prone boundary. Use one reusable client, explicit timeouts, bounded concurrency, response limits, and a typed adapter that keeps transport details away from gameplay code.

## Requests

- Create one client with connection and request timeouts.
- Build URLs safely and encode query values.
- Set a descriptive user agent where the provider requests one.
- Send secrets in the provider's supported authorization mechanism, never logs or chat.

## Responses

- Check status codes before decoding.
- Cap response body sizes and validate content types.
- Parse into transport DTOs, validate, then map to domain values.
- Handle rate limiting, transient server errors, invalid JSON, and timeouts separately.

## Caching and resilience

- Cache successful stable data with an expiry.
- Use backoff with jitter for retryable failures; do not retry unsafe writes blindly.
- Bound the queue and fail fast when the dependency is unhealthy.
- Apply results on the main thread only after revalidating the requesting player/session.

## Example

```java
HttpRequest request = HttpRequest.newBuilder(uri)
    .timeout(Duration.ofSeconds(5))
    .header("Accept", "application/json")
    .GET()
    .build();

client.sendAsync(request, HttpResponse.BodyHandlers.ofString())
    .thenApply(response -> apiAdapter.parse(response.statusCode(), response.body()));
```

## Failure checklist

- Define timeouts, limits, and ownership at the boundary.
- Validate decoded values before they reach gameplay logic.
- Make retries and duplicate delivery idempotent where necessary.
- Close clients, pools, executors, and registrations during disable.
