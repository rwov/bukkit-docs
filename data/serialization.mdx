# Serialization

Serialization converts domain values into stable primitives or maps. The serialized shape is a public data contract: version it, validate it, and do not leak live Bukkit objects into long-lived storage.

## Choose a shape

- Use strings, booleans, numbers, lists, and maps that YAML or your database can represent predictably.
- Store UUIDs and namespaced keys as strings.
- Store locations as world UUID/name plus coordinates and rotation, not a retained `World` object.
- Avoid Java native serialization for long-lived plugin data.

## ConfigurationSerializable

- Implement `ConfigurationSerializable` only when integration with Bukkit YAML is useful.
- Return a map containing an explicit version and required fields.
- Register aliases/types before loading data that depends on them.
- Treat the deserializing constructor or factory as untrusted input parsing.

## Migration

- Accept old versions explicitly and convert them to the current domain model.
- Reject unknown future versions rather than guessing.
- Write migrated data after successful validation and backup strategy.
- Test round trips, missing fields, malformed values, and renamed worlds.

## Example

```java
public Map<String, Object> serialize() {
    return Map.of(
        "version", 1,
        "owner", owner.toString(),
        "world", worldId.toString(),
        "x", x, "y", y, "z", z
    );
}
```

## Failure checklist

- Define timeouts, limits, and ownership at the boundary.
- Validate decoded values before they reach gameplay logic.
- Make retries and duplicate delivery idempotent where necessary.
- Close clients, pools, executors, and registrations during disable.
