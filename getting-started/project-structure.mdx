# Project structure

Package layout should reveal ownership. A feature should have one obvious place that registers it, one place that performs domain decisions, and narrow adapters for Bukkit or storage.

## A practical layout

- `plugin/` contains the `JavaPlugin` entry point and composition root.
- `feature/<name>/` owns commands, listeners, sessions, and views for one capability.
- `domain/` contains Java logic that does not require a running server.
- `infrastructure/` contains configuration, database, HTTP, and platform adapters.

## Composition root

- Create dependencies in `onEnable()` or a dedicated bootstrap object.
- Pass dependencies through constructors instead of global static access.
- Register listeners and commands after required configuration and dependencies are valid.
- Store closeable feature objects so shutdown is deterministic.

## Boundaries that scale

- Commands and listeners translate Bukkit inputs into domain calls.
- Repositories expose domain-shaped operations rather than SQL or YAML details.
- Do not let every class call `JavaPlugin#getConfig()` directly.
- Prefer cohesive feature packages over generic `managers`, `utils`, and `handlers` folders.

## Done check

Test the final JAR through a clean server start and stop. Treat warnings and shutdown failures as defects, not harmless development noise.
