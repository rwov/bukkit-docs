# Introduction

A plugin is a JAR loaded by the server into the same JVM as the game. Bukkit is the API contract; CraftBukkit is the server implementation behind it; Spigot distributes a performance-focused CraftBukkit build and API; Paper extends that ecosystem with additional APIs and patches.

## Choose the API boundary

- Write ordinary plugin code against `org.bukkit` and `org.spigotmc` interfaces.
- Treat CraftBukkit and net.minecraft.server classes as version-sensitive internals.
- Compile the API as a provided dependency because the server supplies it at runtime.
- Check the server implementation and version before using platform-specific extensions.

## How a plugin reaches the game

- The server discovers `plugin.yml` inside the JAR.
- It creates the declared `JavaPlugin` class and calls lifecycle hooks.
- Your plugin registers commands, listeners, tasks, and services during enable.
- Events and API calls operate on server-owned players, worlds, entities, inventories, and registries.

## Thread and ownership rules

- The main server thread owns most live game state.
- Database, file, and HTTP work should run away from the main thread, then schedule only the result application back on it.
- Store stable identifiers such as UUIDs and namespaced keys across sessions; resolve live objects when needed.
- Release tasks, listeners, services, executors, and connections when the plugin disables.

## Done check

Verify the built artifact from a clean build and test it through a full server start and stop. Record the exact Java, server, and plugin versions when behavior differs between environments.
