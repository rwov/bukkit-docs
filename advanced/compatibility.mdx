# Version compatibility

Compatibility is the intersection of bytecode/JVM support, API signatures, server behavior, data formats, and client protocol. Define the exact range you support and test every release family in that range.

## Compile strategy

- Compile against the oldest API when all required symbols exist there.
- Use separate adapter modules or reflection for APIs introduced later.
- Set the Java release no newer than the oldest supported server JVM.
- Never call a newer method from a class that must load on an older server unless that reference is isolated.

## Feature detection

- Prefer checking for a class, method, registry entry, or platform capability over string version comparisons.
- Create adapters once at startup.
- Keep fallback behavior explicit and user-visible.
- Do not silently accept partial behavior that violates data or security invariants.

## Test matrix

- Start, enable, use core features, disable, and restart on every supported line.
- Test clean installs and upgrades with existing data.
- Test optional dependencies absent and at supported/unsupported versions.
- Publish the tested matrix and drop unmaintained versions deliberately.

## Example

```java
boolean supportsProfiles;
try {
    Class.forName("org.bukkit.profile.PlayerProfile");
    supportsProfiles = true;
} catch (ClassNotFoundException ignored) {
    supportsProfiles = false;
}
ProfileAdapter adapter = supportsProfiles ? new ModernProfileAdapter() : new LegacyProfileAdapter();
```

## Review checklist

- The feature has one clear lifecycle owner.
- Failure paths are observable and preserve valid previous state.
- Resource, queue, cache, and loop bounds are explicit.
- The final built JAR is tested on every claimed server line.
