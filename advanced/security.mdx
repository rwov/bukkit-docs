# Security

Treat commands, chat, inventory actions, configuration, plugin messages, database rows, HTTP responses, and cross-plugin calls as untrusted until validated for the specific operation.

## Authorization

- Check the precise permission at the final action boundary.
- Validate resource ownership separately from permission.
- Re-check after delays, UI sessions, or async work.
- Protect alternate entry points such as events, public services, and plugin messages.

## Input and state

- Parse into typed bounded values; reject oversized strings, invalid worlds, non-finite coordinates, and unknown keys.
- Use prepared SQL statements and safe URL construction.
- Use PDC or server-side session identity for custom items/UI, not player-editable names.
- Validate the current inventory, balance, cooldown, and transaction state before commit.

## Abuse resistance

- Rate-limit expensive commands and network actions by stable identity.
- Use nonce/request IDs and expiry for confirmations.
- Make valuable grants idempotent and auditable.
- Keep secrets outside published JARs and redact them from logs.

## Example

```java
if (!player.hasPermission("example.purchase")) return;
PurchaseSession session = sessions.get(player.getUniqueId());
if (session == null || session.expired() || !session.nonce().equals(clickedNonce)) return;
if (!catalog.contains(session.itemId())) return;
purchases.commitOnce(session.transactionId(), player.getUniqueId(), session.itemId());
```

## Review checklist

- The feature has one clear lifecycle owner.
- Failure paths are observable and preserve valid previous state.
- Resource, queue, cache, and loop bounds are explicit.
- The final built JAR is tested on every claimed server line.
