# NMS and internals

NMS and CraftBukkit expose implementation details outside Bukkit's compatibility contract. Use them only when the supported API cannot express the feature and the maintenance cost is accepted.

## Decision order

- Use Bukkit/Spigot API first.
- Use a well-maintained platform extension or protocol library when it provides the needed stable abstraction.
- Use reflection or NMS behind a narrow adapter only for an explicit unsupported capability.
- Require a client mod when the desired client behavior cannot be represented by vanilla protocol/assets.

## Contain the dependency

- Keep version-specific code in a separate package or module.
- Expose your own stable interface to the rest of the plugin.
- Detect the server version/capability once during startup.
- Fail the feature cleanly instead of crashing unrelated plugin behavior.

## Testing and releases

- Compile and run against every claimed server version.
- Test mappings, signatures, serialization, entity metadata, and packet behavior after upgrades.
- Do not parse package names as the only version strategy when feature detection is possible.
- Document that minor server updates may require a plugin release.

## Example

```java
public interface TitleTransport {
    void send(Player player, String title, String subtitle);
}

TitleTransport transport = adapters.createTitleTransport(serverCapabilities)
    .orElseThrow(() -> new IllegalStateException("No supported title transport"));
```

## Review checklist

- The feature has one clear lifecycle owner.
- Failure paths are observable and preserve valid previous state.
- Resource, queue, cache, and loop bounds are explicit.
- The final built JAR is tested on every claimed server line.
