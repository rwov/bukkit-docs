# Memory safety

Plugin leaks are usually ownership leaks: a long-lived map, task, listener, thread, callback, or third-party registry still references a player, world, feature, or old plugin classloader.

## Common roots

- Static collections containing plugin or Bukkit objects.
- Executors and threads whose context classloader or tasks reference plugin classes.
- Repeating tasks, listeners, services, commands, and callbacks not released at feature shutdown.
- Unbounded caches keyed by UUID, chunk, location, or external input.

## Store stable data

- Prefer UUIDs and immutable records to `Player` or `Entity` references.
- Remove per-player sessions on quit/kick and replace them on reconnect.
- Use bounded/expiring caches with explicit invalidation.
- Do not retain whole chunks, worlds, inventories, or configuration trees when small values suffice.

## Diagnose

- Compare heap histograms over time under a repeatable join/quit or reload cycle.
- Inspect dominator paths from retained objects to GC roots.
- Look for old plugin classloaders after disable/reload.
- Fix the owner that should release the reference rather than adding arbitrary null assignments.

## Example

```java
@EventHandler
public void onQuit(PlayerQuitEvent event) {
    UUID id = event.getPlayer().getUniqueId();
    Session removed = sessions.remove(id);
    if (removed != null) removed.close();
}

@Override
public void close() {
    sessions.values().forEach(Session::close);
    sessions.clear();
}
```

## Review checklist

- The feature has one clear lifecycle owner.
- Failure paths are observable and preserve valid previous state.
- Resource, queue, cache, and loop bounds are explicit.
- The final built JAR is tested on every claimed server line.
