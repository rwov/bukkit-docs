# Performance engineering

A healthy server normally has 50 ms to complete each tick. Optimize measured tick-time cost, allocation, I/O, and frequency rather than guessing from code style.

## Measure first

- Capture timings, profiler traces, or Java Flight Recorder data during a representative load.
- Separate one-time startup cost from hot event, task, generation, and packet paths.
- Record call count as well as total and worst-case duration.
- Reproduce with the final JAR and realistic player/entity/world counts.

## Reduce work

- Return early and narrow event filters.
- Replace global scans with indexes updated by lifecycle events.
- Use squared distances, bounded radii, and chunk-aware partitioning.
- Cache only stable or explicitly invalidated results.

## Spread work

- Batch large world edits across ticks with a fixed budget.
- Move blocking I/O off-thread without moving live Bukkit access.
- Coalesce UI updates and skip unchanged values.
- Apply backpressure to database/HTTP queues instead of accepting unlimited work.

## Example

```java
long start = System.nanoTime();
int processed = 0;
while (processed < blocksPerTick && iterator.hasNext()) {
    apply(iterator.next());
    processed++;
}
long micros = TimeUnit.NANOSECONDS.toMicros(System.nanoTime() - start);
if (micros > budgetMicros) plugin.getLogger().fine("Edit batch took " + micros + " us");
```

## Review checklist

- The feature has one clear lifecycle owner.
- Failure paths are observable and preserve valid previous state.
- Resource, queue, cache, and loop bounds are explicit.
- The final built JAR is tested on every claimed server line.
