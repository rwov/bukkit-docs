# Testing plugins

Use the cheapest test that can catch the failure: unit tests for pure rules, adapter tests for serialization/SQL, and real-server integration tests for lifecycle and Bukkit behavior.

## Unit tests

- Keep domain rules independent of static Bukkit access.
- Test boundaries, invalid inputs, permissions expressed as domain capabilities, and idempotency.
- Use deterministic clocks and random sources.
- Do not mock large parts of Bukkit just to recreate a server poorly.

## Adapter tests

- Round-trip configuration and persistent formats.
- Run repository tests against the actual database engine where SQL behavior matters.
- Test migration from every supported schema version.
- Verify HTTP decoding with captured minimal fixtures and error responses.

## Server tests

- Build the final JAR, start a real supported server, and inspect enable logs.
- Exercise commands, events, scheduler transitions, joins/quits, worlds, and shutdown.
- Assert no duplicate registration after restart.
- Preserve logs and server/plugin versions as test artifacts.

## Example

```java
@Test
void duplicateClaimIsIdempotent() {
    RewardLedger ledger = new InMemoryRewardLedger();
    ClaimId claim = new ClaimId(UUID.randomUUID());
    assertTrue(ledger.claimOnce(claim, playerId, reward));
    assertFalse(ledger.claimOnce(claim, playerId, reward));
    assertEquals(1, ledger.deliveries().size());
}
```

## Review checklist

- The feature has one clear lifecycle owner.
- Failure paths are observable and preserve valid previous state.
- Resource, queue, cache, and loop bounds are explicit.
- The final built JAR is tested on every claimed server line.
