# Troubleshooting handbook

Troubleshoot by narrowing the failing boundary. Preserve the full log, exact reproduction, versions, configuration, and recent change before editing code.

## Plugin will not enable

- Find the first exception belonging to the plugin.
- Check `plugin.yml`, entry class, Java bytecode version, missing libraries, and hard dependencies.
- Verify the JAR being tested is the newly built artifact.
- Reproduce after a full stop/start, not only a hot reload.

## Feature fails at runtime

- Confirm the command/event path actually ran.
- Log stable identifiers and state transitions around the failure.
- Check thread ownership, cancellation, permissions, object validity, and configuration values.
- Minimize other plugins and data until the smallest reproducer remains.

## Lag or memory growth

- Profile during the actual slow period.
- Check hot handler frequency, unbounded loops/queues/caches, blocking I/O, and repeated allocations.
- Inspect retained plugin classloaders and per-player state after quit.
- Validate that disable closes tasks, threads, pools, listeners, and services.

## Data failures

- Back up before repair.
- Check schema/config versions and migration logs.
- Make repairs idempotent and report changed records.
- Do not silently replace malformed production data with defaults.

## Example

```java
getLogger().log(Level.SEVERE,
    "Failed to load home {0} for player {1}; configVersion={2}",
    new Object[] { homeName, playerId, settings.version() });
// Log the throwable with a separate Level.SEVERE call when one exists.
```

## Review checklist

- The feature has one clear lifecycle owner.
- Failure paths are observable and preserve valid previous state.
- Resource, queue, cache, and loop bounds are explicit.
- The final built JAR is tested on every claimed server line.
