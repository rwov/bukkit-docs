# Configuration

Bukkit's configuration API is a tree of loosely typed values. Convert that tree into a validated immutable settings object before feature code uses it.

## Defaults and files

- Place `config.yml` in resources and call `saveDefaultConfig()` once.
- Use `getConfig()` for the primary YAML file.
- Use `YamlConfiguration.loadConfiguration(file)` for additional files.
- Do not overwrite an administrator's file just to add newly introduced defaults.

## Read defensively

- Check required paths and types; `getInt` returning zero can hide a missing key.
- Clamp ranges and validate materials, worlds, durations, URLs, and enum names.
- Report all validation errors together when possible.
- Keep runtime code dependent on typed settings, not scattered string paths.

## Safe reload

- Load and validate a new configuration without mutating active state.
- If validation fails, keep the old settings and report exact paths.
- Atomically swap the settings reference after successful validation.
- Restart or reconcile tasks and sessions whose behavior depends on changed values.

## Example

```java
public record Settings(int radius, Duration cooldown) {
    static Settings load(FileConfiguration config) {
        int radius = config.getInt("search-radius", -1);
        long seconds = config.getLong("cooldown-seconds", -1);
        if (radius < 1 || radius > 128) {
            throw new IllegalArgumentException("search-radius must be 1..128");
        }
        if (seconds < 0) {
            throw new IllegalArgumentException("cooldown-seconds must be >= 0");
        }
        return new Settings(radius, Duration.ofSeconds(seconds));
    }
}
```

## Production check

- Validate inputs and capabilities before mutation.
- Keep hot-path work bounded and observable.
- Re-check live state after any delay or asynchronous boundary.
- Clean up every resource owned by the feature during disable.
