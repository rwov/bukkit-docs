# Scheduler

The scheduler coordinates work with server ticks. Synchronous tasks run on the main thread; asynchronous tasks run elsewhere and must not freely touch live Bukkit state.

## Timing

- One server tick is normally 50 ms, but lag stretches real elapsed time.
- Use ticks for game sequencing and wall-clock time for real deadlines.
- A repeating task's period controls scheduling, not guaranteed real-time precision.
- Keep and cancel the returned `BukkitTask` when the feature ends.

## Sync versus async

- Use sync tasks for players, worlds, entities, inventories, and most Bukkit APIs.
- Use async work for blocking database, file, or HTTP operations and isolated CPU work.
- Snapshot only the primitive or immutable data needed before leaving the main thread.
- Schedule a sync continuation and re-resolve/revalidate state before applying results.

## Cancellation

- Cancel tasks when their session, world, entity, or feature ends.
- A task may cancel itself when its terminal condition is met.
- Do not create one repeating task per object when one bounded coordinator can update many.
- `BukkitScheduler#cancelTasks(plugin)` is a final safety net, not a replacement for ownership.

## Example

```java
UUID playerId = player.getUniqueId();
Bukkit.getScheduler().runTaskAsynchronously(plugin, () -> {
    Profile profile = repository.load(playerId);
    Bukkit.getScheduler().runTask(plugin, () -> {
        Player current = Bukkit.getPlayer(playerId);
        if (current == null || !current.isOnline()) return;
        sessions.open(current, profile);
    });
});
```

## Production check

- Validate inputs and capabilities before mutation.
- Keep hot-path work bounded and observable.
- Re-check live state after any delay or asynchronous boundary.
- Clean up every resource owned by the feature during disable.
