# Permissions

Permissions answer whether a sender may perform an action. They are authorization checks, not feature flags and not a substitute for validating state or ownership.

## Design nodes

- Use a stable namespace such as `example.kit.claim`.
- Prefer action-oriented nodes over implementation details.
- Declare descriptions and defaults in `plugin.yml`.
- Use child relationships for convenience groups, but check the precise action node in code.

## Defaults

- `true` grants to everyone; use only for harmless behavior.
- `op` grants to operators by default and is not a fine-grained production policy.
- `false` requires an explicit grant.
- `not op` is unusual and should be documented clearly.

## Runtime checks

- Call `Permissible#hasPermission` at the moment the action runs.
- Re-check after delays or async work because roles can change.
- Permission attachments are temporary runtime overrides; remove plugin-owned attachments on cleanup.
- A command metadata permission does not protect alternate entry paths such as events or APIs.

## Example

```java
if (!player.hasPermission("example.home.teleport")) {
    player.sendMessage("You do not have permission to teleport home.");
    return;
}

Home home = homes.find(player.getUniqueId(), requestedName);
if (home == null || !home.owner().equals(player.getUniqueId())) return;
teleports.start(player, home.location());
```

## Production check

- Validate inputs and capabilities before mutation.
- Keep hot-path work bounded and observable.
- Re-check live state after any delay or asynchronous boundary.
- Clean up every resource owned by the feature during disable.
