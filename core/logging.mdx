# Logging and diagnostics

Logs should explain what the plugin attempted, which stable identifiers were involved, and what an administrator can do next. Avoid both silent failure and per-tick noise.

## Use the plugin logger

- Call `getLogger()` so messages carry the plugin name.
- Use INFO for meaningful lifecycle and administrator-facing state changes.
- Use WARNING for degraded but continuing behavior.
- Use SEVERE with the throwable for failures that prevent or corrupt a feature.

## Structured context

- Include operation names, UUIDs, world names, keys, and durations where relevant.
- Do not log access tokens, database passwords, cookies, chat secrets, or full personal data.
- Rate-limit repeated failures and summarize suppressed counts.
- Keep a debug mode targeted; do not turn every event into an unconditional log line.

## Support bundle

- Report plugin version, server implementation/build, Java version, operating system, and relevant dependency versions.
- Include a redacted configuration summary and full stack trace.
- Record whether the failure occurs after clean startup or only after reload.
- Expose health state for executors, queues, pools, and migrations when those systems exist.

## Example

```java
long started = System.nanoTime();
try {
    migrationRunner.migrate();
    long millis = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - started);
    getLogger().info("Database migrations completed in " + millis + " ms");
} catch (SQLException ex) {
    getLogger().log(Level.SEVERE, "Database migration failed; disabling storage", ex);
}
```

## Production check

- Validate inputs and capabilities before mutation.
- Keep hot-path work bounded and observable.
- Re-check live state after any delay or asynchronous boundary.
- Clean up every resource owned by the feature during disable.
